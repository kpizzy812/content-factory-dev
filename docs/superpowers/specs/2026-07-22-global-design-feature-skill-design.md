# Глобальный skill `design-feature` для Codex

Дата: 22 июля 2026 года.

## 1. Цель

Создать глобальный Codex skill `$design-feature`, который автономно проектирует UI/UX-фичу до уровня проверенного интерактивного макета. Skill не изменяет продуктовый код. Его результатом являются визуальные концепты, HTML-макет, Playwright-проверки, история независимой критики и полная спецификация последующей интеграции.

Skill должен подходить для разных репозиториев и при этом всегда опираться на фактическую дизайн-систему текущего проекта.

## 2. Границы

Skill выполняет:

- анализ задачи, пользователей и сценариев;
- чтение `AGENTS.md`, продуктовой документации, дизайн-токенов, оболочки и эталонных экранов;
- создание визуальных направлений через ImageGen;
- создание интерактивного HTML-макета;
- браузерную проверку через Playwright;
- независимый разбор скриншотов четырьмя критиками;
- итерационные исправления макета;
- подготовку спецификации реализации.

Skill не выполняет:

- интеграцию макета в приложение;
- изменение продуктовых компонентов, роутов, API, базы данных и прав;
- публикацию, деплой, merge или PR продуктовой реализации;
- объявление результата готовым без реального запуска Playwright.

## 3. Вход и запуск

Явный запуск:

```text
$design-feature "раздел, где оператор видит застрявшие пайплайны и их стоимость"
```

Один запуск проектирует одну связанную поверхность. Формулировка описывает пользовательскую задачу, а не заранее выбранную раскладку элементов.

В проектах, где этот процесс обязателен для всей UI-работы, `AGENTS.md` должен явно требовать `$design-feature` перед изменением продуктового интерфейса.

## 4. Артефакты

Все результаты сохраняются в `design-preview/<feature-slug>/`:

```text
design-preview/<feature-slug>/
  brief.md
  concepts/
    concept-01.png
    concept-02.png
    concept-03.png
    selection.md
  mockup.html
  mockup.spec.ts
  playwright.config.ts
  implementation-spec.md
  review-log.md
  screenshots/
    round-01/
    round-02/
    final/
```

Для большого домена skill сначала читает, а при отдельной явно поставленной задаче создаёт системный уровень:

```text
design-preview/_system/
  map.md
  glossary.md
  components.html
  tokens.css
```

Экран не может вводить новые общие статусы, сущности или компоненты в обход `_system`.

## 5. Рабочий процесс

### 5.1 Сбор контекста

Codex сначала определяет корень репозитория и читает применимые инструкции. Затем находит:

- продуктовую документацию и словарь предметной области;
- существующую оболочку, маршрутизацию и навигацию;
- дизайн-токены, шрифты, цвета, радиусы, тени и сетку;
- общие UI-компоненты;
- один-два свежих эталонных экрана;
- доступные данные, роли и состояния;
- существующую конфигурацию Playwright.

Если есть `design-preview/_system/`, он читается до проектирования конкретной поверхности.

В `brief.md` фиксируются пользователь, основная задача, сценарии, ограничения, обязательные состояния, реальные данные и сделанные допущения.

### 5.2 Визуальные направления через ImageGen

ImageGen создаёт два-три осмысленно различающихся визуальных направления на основе одного брифа и реальных правил проекта. Концепты нужны для выбора композиции, иерархии и визуального характера, но не считаются точной спецификацией текста или поведения.

Codex сравнивает концепты по следующим критериям:

- скорость решения основной пользовательской задачи;
- информационная иерархия;
- соответствие дизайн-системе;
- масштабируемость на реальные данные и состояния;
- пригодность для desktop и mobile.

Выбор и причины фиксируются в `concepts/selection.md`. Если ImageGen недоступен, skill фиксирует причину и продолжает с текстовыми визуальными направлениями; этот fallback не отменяет HTML- и Playwright-этапы.

### 5.3 Интерактивный HTML-макет

Выбранное направление переносится в `mockup.html`. HTML является источником истины, а изображения ImageGen остаются референсами.

Макет должен:

- использовать реальные токены и паттерны проекта;
- быть интерактивным без подключения к продуктовым API;
- содержать реалистичные локальные данные;
- показывать обычное, пустое, loading, error, partial и large-data состояния;
- показывать disabled, hover, focus, validation и confirmation состояния контролов;
- поддерживать desktop, tablet и mobile;
- не требовать изменения продуктового приложения.

Встроенный переключатель сценариев может использоваться для воспроизводимого открытия состояний из Playwright.

### 5.4 Проверка Playwright

Skill использует существующий Playwright проекта. Если его нет или браузер не установлен, результат нельзя объявлять готовым: skill сообщает точную блокировку вместо имитации визуальной проверки.

Рядом с макетом создаётся изолированный `playwright.config.ts` с `testDir` текущего каталога. Поэтому проверка не зависит от того, где основной проект хранит E2E-тесты, и не требует добавлять временный mock-тест в продуктовый `tests/`. Команда запуска определяется по package manager проекта и явно записывается в `review-log.md`.

`mockup.spec.ts` проверяет:

- загрузку макета без ошибок страницы и консоли;
- основные пользовательские действия и переходы между состояниями;
- отсутствие горизонтального переполнения и обрезанного важного контента;
- desktop, tablet и mobile viewport;
- клавиатурный фокус и базовую семантику интерактивных элементов;
- отображение пустого, loading, error, partial и large-data состояний;
- визуальные скриншоты каждого проверяемого состояния.

Скриншоты сохраняются отдельно для каждого раунда. Критика проводится только по фактически отрисованному результату.

## 6. Четыре независимых критика

На каждом раунде запускаются четыре независимых субагента. Каждый получает `brief.md`, актуальный HTML, Playwright-результаты и скриншоты текущего раунда.

1. Критик состояний и полноты проверяет все состояния, данные, контролы, ошибки и тупики.
2. Продуктовый UX-критик проходит реальный рабочий сценарий пользователя, ищет лишние шаги, слабую иерархию и недостаток контекста для решения.
3. Критик адаптивности и доступности проверяет mobile/tablet, touch targets, клавиатуру, фокус, читаемость, overflow и семантику.
4. Критик дизайн-системы читает реальные токены, общие компоненты, эталонные экраны и `_system/glossary.md`, после чего находит визуальные и терминологические расхождения.

Критик возвращает либо конкретный список в формате «проблема → влияние → исправление → доказательство», либо ровно `критики нет`. Вкусовые замечания без связи с задачей, эвристикой или правилом проекта отбрасываются.

## 7. Итерационный цикл и завершение

Основной агент агрегирует замечания, удаляет дубли, сортирует их по влиянию и исправляет макет. После каждого изменения он заново запускает Playwright и создаёт новый набор скриншотов, а критики оценивают только свежий результат.

Успешное завершение требует одновременно:

- зелёного Playwright E2E;
- отсутствия blocker, critical и major замечаний;
- двух последовательных раундов, где все критики вернули `критики нет` или только обоснованную косметику.

Жёсткий предел — десять раундов. Если он достигнут, skill останавливается честно, перечисляет незакрытые замечания и не называет макет идеальным или завершённым.

## 8. Спецификация интеграции

`implementation-spec.md` описывает всё необходимое для последующей реализации другим заданием:

- назначение экрана и пользовательские сценарии;
- структура интерфейса и переиспользуемые компоненты;
- состояния и переходы;
- необходимые модели, поля и API-контракты;
- права доступа и необратимые действия;
- валидация, ошибки и recovery;
- аналитические события;
- responsive-поведение;
- acceptance criteria и нужные продуктовые E2E;
- явный список решений, которые пока являются mock-only.

Спецификация не должна выдавать несуществующие API или модели за уже реализованные.

## 9. Итоговый отчёт

Skill сообщает:

- где лежат концепты, HTML, скриншоты, Playwright-тест и спецификация;
- почему выбран конкретный концепт;
- сколько прошло раундов;
- какие существенные проблемы нашли и исправили;
- итог Playwright;
- какие замечания остались;
- что именно потребуется для интеграции.

## 10. Применение к ContentFactory

ContentFactory уже использует Nuxt 4, Vue, Bun и Playwright. Конфигурация проекта проверяет четыре viewport: 1920×1080, 1280×800, 768×1024 и 375×812. Проектный `AGENTS.md` должен закрепить:

- обязательный запуск `$design-feature` перед созданием или существенной переработкой UI-раздела;
- запрет интегрировать mockup в продуктовый код в рамках design-задачи;
- чтение `design-preview/_system/` до экранов большого домена;
- сохранение всех дизайн-артефактов в репозитории;
- отдельное последующее задание на продуктовую реализацию.

## 11. Критерий готовности самого skill

Глобальный skill считается готовым, когда:

- Codex обнаруживает его как `$design-feature`;
- структура и frontmatter проходят проверку skill-creator;
- ссылки на references и assets разрешаются;
- инструкция однозначно запрещает изменение продуктового кода;
- ImageGen имеет явный fallback;
- Playwright является обязательным gate;
- локальная Playwright-конфигурация находит mock-тест независимо от проектного `testDir`;
- четыре критика имеют непересекающиеся оптики и строгий формат ответа;
- завершение требует двух чистых раундов и ограничено десятью;
- тестовый сухой прогон подтверждает выбор правильных файлов и команд без изменения приложения.
