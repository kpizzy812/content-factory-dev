# ZavodCamp — Compliance Position

> Документ описывает зону ответственности платформы и оператора при автоматизированном маркетинговом постинге через социальные сети. Применяется ко всем модулям загрузки в соцсети и к подсистемам Indigo / прокси.

---

## Что мы делаем (наша зона)

- **Маркетинговая автоматизация** в собственных коммерческих интересах: продвижение собственных мобильных приложений, повторяемая публикация креативов на привязанных аккаунтах оператора.
- **Использование платформенных API и web-интерфейсов** техническими средствами автоматизации (browser automation, headless-сессии, cookie-management через антидетект-окружение).
- **Обработка данных собственных аккаунтов**, созданных нами, либо приобретённых легально, либо переданных оператору в рамках бизнес-договорённости.
- **Прокси-инфраструктура**: легально арендованные mobile/residential/datacenter прокси у проверенных провайдеров, для маскировки IP-инфраструктуры серверов и приведения трафика аккаунтов к географии целевой аудитории.
- **Шифрование секретов аккаунтов** (логины, пароли, 2FA-секреты, прокси-credentials) на уровне БД с журналируемым доступом операторов.

---

## Что мы НЕ делаем (вне зоны)

- **Массовый spam** вне маркетинговых целей продукта оператора.
- **Покупка взломанных, угнанных, восстановленных без разрешения владельца аккаунтов.** Аккаунт принимается к интеграции только при подтверждении легальности происхождения.
- **Атаки на конкурентов** через массовые жалобы, координированные дизлайки, скоординированный негативный комментинг.
- **Распространение скам-контента, фишинга, дезинформации, нелегальных товаров и услуг.**
- **Сбор PII третьих лиц** (e-mail, телефонов, контактов аудитории) без законного основания.
- **Обход региональных блокировок** (санкционные списки, geo-restricted сервисы) с целью предоставления услуг ограниченным аудиториям.

## Взаимодействие с Terms of Service платформ

Платформенные ToS (TikTok, YouTube, Instagram, Meta) принимаются оператором при создании / приобретении каждого аккаунта. Технические средства автоматизации применяются в рамках разумной маркетинговой деятельности с учётом следующих ограничений:

- Частота публикаций соблюдает рекомендованные платформой лимиты (типично — не более 3-5 публикаций в день на аккаунт без специального бизнес-доступа).
- Контент проходит модерацию платформы; платформа имеет полное право удалить, ограничить или забанить аккаунт.
- При получении уведомления от платформы об ограничении — оператор обязан остановить активность аккаунта в ZavodCamp вручную.

**Юридическая ответственность за нарушения ToS платформ остаётся на операторе** (физическое или юридическое лицо, владеющее аккаунтом). ZavodCamp как инструмент не принимает на себя ответственность за действия оператора, выходящие за рамки документированных best-practices.

## Защита секретов

| Категория секрета | Где хранится | Уровень защиты |
|-------------------|--------------|----------------|
| Пароли соц-аккаунтов | `SocialAccount.loginPassword` | AES-256-GCM, ENCRYPTION_KEY |
| 2FA TOTP секреты | `SocialAccount.twoFASecret` | AES-256-GCM |
| Recovery email/phone | `SocialAccount.recoveryEmail/Phone` | AES-256-GCM |
| OAuth tokens | `SocialAccount.accessToken/refreshToken` | AES-256-GCM |
| Прокси credentials | `Proxy.host/username/password/rotationUrl` | AES-256-GCM |

Все операции расшифровки секретов журналируются в `SecretAccessLog` с привязкой к userId, IP, причине доступа, типу действия. Журнал — append-only, не редактируется и не удаляется после записи.

API ZavodCamp **никогда не возвращает расшифрованные секреты** в HTTP responses без явного действия `reveal` от оператора. Операция `reveal` требует:
1. Активной сессии оператора с правом `canRead` для модуля.
2. Указания причины (free-text reason).
3. Записи в `SecretAccessLog` ДО возврата открытого значения.

### Управление ENCRYPTION_KEY

Потеря `ENCRYPTION_KEY` = инцидент с потерей данных уровня "high": все шифрованные login-секреты, OAuth токены и прокси-credentials становятся **невосстановимы** и аккаунты придётся заводить заново.

Mitigation:
- Ключ хранится в password manager у двух независимых maintainer'ов; production и dev окружения используют разные ключи.
- Генерация — `openssl rand -hex 32`; формат и инструкции — `.env.example` и `docs/architecture/social_automation.md` раздел "Setup и backup".
- Плановая ротация раз в год через `scripts/rotate-encryption-key.ts` (создаётся в итерации 2 при production deployment) с поддержкой `OLD_ENCRYPTION_KEY` для одноразовой миграции данных.
- Внеплановая ротация — при подтверждённой компрометации серверного окружения (см. процедуру в "Утечки и инциденты" ниже).

## Утечки и инциденты

При обнаружении компрометации (утечка прокси, раскрытие IP сервера, фишинг операторской почты) применяется процедура:

1. Немедленный отзыв прокси / OAuth токенов / паролей затронутых аккаунтов.
2. Telegram-алерт на критический канал (`critical_error`).
3. Ротация `ENCRYPTION_KEY` при подтверждённой компрометации серверного окружения (см. `docs/architecture/social_automation.md` раздел Encryption rotation).
4. Запись инцидента в `AgentLog` с `level=error` и описанием root cause.
