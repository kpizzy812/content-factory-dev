# Авторизация

ContentFactory логинит пользователей сам. Родительская платформа MarketingCamp осталась в коде как необязательный адаптер для установок, где она действительно есть, и больше не является источником истины.

## Два провайдера

Выбор — переменная `AUTH_PROVIDER`.

| Значение | Поведение |
| --- | --- |
| `local` (по умолчанию) | Пароль проверяется по `ZavodUser.passwordHash`. Права назначаются внутри системы. |
| `marketingcamp` | Вход делегируется родительской платформе, RBAC-поля перезатираются её ответом при каждом логине. |

Пустое значение читается как `local`. Неизвестное значение роняет запрос с явной ошибкой, а не откатывается молча — конфигурация не должна течь незаметно.

## Первый администратор

```bash
bun run create:admin owner@example.com "длинный пароль не короче 12"
```

Скрипт идемпотентен: повторный запуск обновляет пароль и права уже существующей учётки, id не меняется. Пароль передаётся аргументом и не пишется в логи.

## Учётки и пароли

- создание: `POST /api/admin/users` с телом `{ email, password, name?, surname?, rolePreset?, moduleAccess? }`;
- смена пароля: `PUT /api/admin/users/:id/password` с телом `{ password }`;
- блокировка: `PUT /api/admin/users/:id` с `{ isActive: false }` — работает при любом провайдере.

Оба эндпоинта требуют `canAdmin`.

## Политика пароля

- минимум 12 символов;
- scrypt из `node:crypto`, параметры `N=16384, r=8, p=1`, ключ 64 байта;
- своя случайная соль 16 байт на каждую учётку, поэтому один и тот же пароль даёт разные хеши;
- формат хранения `scrypt$N$r$p$saltBase64$hashBase64`;
- сравнение константное по времени.

Внешних зависимостей для хеширования нет — только стандартная библиотека Node.

## Что наружу не отдаётся

`passwordHash` не входит в `PUBLIC_USER_SELECT` (`server/utils/auth/user-select.ts`), которым пользуются `GET /api/admin/users`, `GET /api/admin/users/:id` и `PUT /api/admin/users/:id`. Ответ логина содержит только поля сессии: `id`, `externalId`, `email`, `name`, `surname`, `rolePreset`.

Ответ на неизвестный email и на неверный пароль одинаков — форма входа не работает как оракул существующих учёток. Для отсутствующей учётки проверка пароля всё равно прогоняется вхолостую, чтобы время ответа не выдавало её отсутствие.

## Чем это отличается от dev-логина и тестового bypass'а

| Механизм | Когда работает | Зачем |
| --- | --- | --- |
| Локальный вход | `AUTH_PROVIDER=local` | Штатный вход пользователей. |
| Dev-логин | `CONTENT_FACTORY_ENV=development` и `DEV_AUTH_ENABLED=true` с заданными email и паролем | Изолированная разработка без БД пользователей. Проверяется до провайдера. |
| `TEST_AUTH_BYPASS` | `NODE_ENV != production` и заголовки `x-test-auth-token` + `x-test-user-id` | Тесты. В проде не активируется. |

Локальные учётки и dev-логин выводят `externalId` из email одинаково, поэтому одна почта не может дать два разных аккаунта.

## Перевод установки с MarketingCamp на local

1. Выставить `AUTH_PROVIDER=local`.
2. Назначить пароли существующим учёткам: `PUT /api/admin/users/:id/password`. Учётки, пришедшие из MarketingCamp, имеют `passwordHash = null` и без пароля войти не смогут.
3. Убедиться, что нужные пользователям права проставлены локально — при `local` они больше не приезжают извне и не перезатираются при входе.
4. Убрать `MARKETING_CAMP_URL`, если обмен идеями тоже не нужен (см. `LEGACY_MARKETING_CAMP_SYNC_ENABLED` в `docs/operations/legacy-contour.md`).
