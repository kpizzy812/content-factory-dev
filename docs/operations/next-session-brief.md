## Важно: приоритет изменился 14.08 вечером

Заказчик подтвердил, что **сырые видеоисходники Лианы есть**. Это переворачивает порядок: основной путь — липсинк по её реальным фрагментам, где подменяется только артикуляция, а мимика, взгляд и свет остаются настоящими. Аватар из фото остаётся запасным путём для сцен, под которые не нашлось фрагмента.

Заказчик отдельно высказал сомнение: «аватары все кривые выходят, а тут ещё и из фото». Возражение справедливое для оживления портрета и несправедливое для липсинка по видео — это разные механизмы. Ответ на него даёт не переписка, а canary: одна и та же реплика через липсинк по её фрагменту и через аватар из фото, рядом.

Поэтому порядок теперь такой: сначала прогон живого пути на её материале, потом canary со сравнением двух подходов, и только затем всё остальное.

Способность `image_to_image` и вариации портрета доделаны параллельной сессией и описаны в пункте 1 — заново их не начинать. На новый приоритет это не влияет: вариации нужны там, где фрагмента под сцену не нашлось.

## Что делать, по порядку

### 0. Прогон живого пути на материале Лианы (первое)

Загрузить сырые записи в библиотеку исходников (`POST /api/characters/:id/source-recordings` — сервер сам режет по границам сцен, до 2 ГБ за раз), проверить, сколько фрагментов приняла нарезка и сколько отбраковала как дубли по перцептивному хэшу. На однородной съёмке отбраковка большая — это измеренный факт, см. `presenter-library.md`.

Затем собрать ролик целиком: сцены ведущей через липсинк, перебивки из кадров, инфографика поверх. Это первый живой прогон всего, что сделано 14.08, — ожидать проблем на стыках.

### 1. Портреты из одного референса — СДЕЛАНО 14.08 вечером

Этап 5 спецификации `docs/superpowers/specs/2026-08-14-avatar-pipeline.md` закрыт. Что лежит в коде:

- **Способность `image_to_image`** — референс плюс инструкция правки, на выходе кадр того же человека. Схемы сняты с `https://replicate.com/api/models/<owner>/<name>/versions`, **цены — из `billingConfig` в HTML страницы модели** (`https://replicate.com/<owner>/<name>`): публичный API тарифы не отдаёт вовсе, а страница отдаёт, и токен для неё не нужен. Включены три Kontext с подтверждённой ценой ($0.025 dev / $0.04 pro / $0.08 max за кадр), по умолчанию dev. `bytedance/flux-pulid` выключен — у него не тариф, а оценка прогона по времени GPU.
- **Идемпотентность вне ролика** — `identityScope` в `runMediaTask` и `subjectScope` в `buildMediaIdentity`. Слот вариации — `character-reference:{refId}:variation:{presetKey}`, повтор слота денег не стоит. Раскладка ключей роликов не тронута. Побочный эффект: снято старое ограничение из `generate-reference.post.ts` — Replicate-модели больше не требуют `videoId`.
- **Пресеты вариаций** — `server/utils/character-reference-variations.ts`: восемь правок по четырём осям (ракурс, одежда, обстановка, свет), все с `kind="face"`, потому что `compareAvatarPortraits` ставит портрет лица впереди прочих кадров и вариация в `body`/`outfit` никогда не была бы выбрана.
- **Эндпоинт** — `POST /api/characters/:id/reference-variations`, тело `{ count?, sourceReferenceId?, modelId?, note?, startIndex? }`. Восемь contract-тестов.
- **Мок Replicate знал пять способностей из семи**: `speech_to_video` завели в прошлой волне, но в `OUTPUT_EXTENSION_BY_CAPABILITY` не добавили — любой прогон аватарной ветки в mock-режиме падал на «no output type». Добавлены обе недостающие.
- **Заглушки fal-мока не работали на холодном кеше**: кеш лежал в `<kind>.bin`, а ffmpeg по такому расширению контейнер выбрать не может («Unable to choose an output format»). На чистой машине падал первый же вызов, и вместе с ним `generate-reference` отдавал 500. На машине с прогретым кешем дефекта не видно — файл уже есть, ffmpeg не зовётся. Из-за этого `image-generation-character.spec.ts` не мог пройти нигде, кроме машины с готовым кешем.

Чего нет: интерфейса. Эндпоинт вызывается только запросом, кнопки «сделать вариации» в карточке персонажа не появилось. И ни одного платного вызова по нему не делалось — сходство лица проверяется только canary.

### 2. DB-сьюты — прогнаны целевым набором

`cf-tests-pg` (порт 5436) поднят, миграции применены: 110 штук, ожидающих нет. Прогнано и зелено:

- `tests/api/character-reference-variations.spec.ts` — 8 тестов;
- `tests/api/image-generation-character.spec.ts`, `tests/api/image-generation-scene.spec.ts`, `tests/integration/replicate-lipsync-flow.spec.ts` — 18 тестов вместе.

Не прогонялось: аватарная ветка целиком (`lip-sync-runner`), перебивки, Remotion — на них DB-сьюта нет, они закрыты чистыми тестами. Полная `tests/unit` идёт около 50 минут — её не запускать без нужды.

Про машину, чтобы не потерять час: API-сьюта поднимает dev-сервер Nuxt. После правки любого серверного файла первая пересборка занимает десятки минут и может встать совсем; повторный прогон без правок укладывается в полторы минуты. Убитый прогон оставляет живой node-процесс с dev-сервером — гасить руками, иначе следующий упирается в занятый порт 24678. И не заворачивать вывод в `| tail` или `| grep`: пайп буферизует всё до конца, прогресс не виден.

### 3. Canary (ждёт пополнения Replicate)

Бюджет утверждён — до $20. Порядок из `docs/operations/replicate.md`:

1. **одна и та же русская реплика тремя способами, рядом**: липсинк по её живому фрагменту, оживление студийного фото, оживление стоп-кадра из её же фрагмента. Это и есть ответ на возражение заказчика про кривые аватары — глазами, а не словами. Заодно снять аватарный вариант в 720p и 1080p и решить разрешение: разница $2.0 против $3.6 за ролик;
2. по одному прогону на `text_to_image`, `text_to_video`, `image_to_video`, `text_to_speech`;
3. повтор каждого запроса — убедиться, что новый платный prediction не появился;
4. один цельный ролик со сценами ведущей и перебивками;
5. замерить, сколько занимает наложение инфографики Remotion (при первом рендере скачается headless Chrome, ~150 МБ).

### 4. Блочная съёмка (решение отложено до canary)

Если модель плохо держит лицо между отдельными сценами — переходить на блоки по 30–60 секунд, для этого включать `fabric-1.0` (60 секунд одним вызовом) после подтверждения его цены. Если держит — оставить посценную съёмку: она позволяет пересобрать одну сцену, не трогая соседние.

## Принятые решения — не переспрашивать

Зафиксированы в `docs/superpowers/specs/2026-08-14-avatar-pipeline.md` §8:

- миграции схемы БД разрешены;
- B-roll — картинка плюс движение камеры, доля около 40%;
- Remotion внедряем, лицензия бесплатна (команда до трёх человек);
- бюджет canary до $20;
- ручная перегенерация сцены оператором не тратит бюджет попыток;
- A/B-варианты пока не делаем;
- число аккаунтов вне нашей зоны, «300 роликов в сутки» — требование к мощности производства.

## Правила работы

- **TDD обязателен**: тест пишется до кода и должен упасть по существу. Так сделана вся эта волна.
- **Проверка**: `bunx vitest run --config vitest.pure.config.ts` (чистая сьюта, ~10 секунд, 118 файлов / 1096 тестов на момент коммита) и `bunx tsc --noEmit -p .nuxt/tsconfig.server.json` — **базовый уровень 72 унаследованные ошибки**, рост означает поломку. Композиции Remotion проверяются отдельно: `bunx tsc --noEmit -p remotion/tsconfig.json`.
- **Схемы моделей и поля чужих API не выдумывать.** Снимать с API или документации и приводить дословно; неподтверждённая цена означает `billingConfirmed: false` и `integrated: false`.
- **Не запускать Workflow** — машина не тянет, процесс падает. Параллельные агенты пачками по два-три через Agent.
- В рабочем дереве могут появляться правки параллельной сессии — не откатывать чужое.
