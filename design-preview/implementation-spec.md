# Спецификация переноса макетов в приложение

Дата: 5 августа 2026 года.
Источник: `design-preview/catalog/` (9 макетов), `design-preview/_system/tokens.css`.
Режим: отдельная ветка, полная замена UI-слоя. Продакшна нет, обратная совместимость интерфейса не требуется.

## 1. Что переписываем

Замеры по текущему коду:

| Что | Сколько |
| --- | --- |
| `.vue` всего | 341 |
| из них с классами DaisyUI | 325 |
| компонентов | 293 |
| страниц | 46 |
| composables | 90 |
| Pinia-сторов | 18 |

DaisyUI используется в 95% файлов, поэтому «постепенная замена» невозможна — переписывается весь слой представления.

## 2. Границы

**Переписывается полностью:**

- `app/components/**` — все 293 компонента
- `app/pages/**` — все 46 страниц
- `app/layouts/**`
- `app/assets/css/main.css`
- зависимости `daisyui` удаляются из `package.json`

**Не трогаем вообще:**

- `server/**` — API, провайдеры, воркеры, планировщики
- `prisma/**` — схема и миграции
- `shared/**` — типы, схемы, чистая логика
- `app/composables/**` — 90 файлов, это слой доступа к API, от вида интерфейса не зависит
- `app/stores/**` — 18 сторов фильтров, переносятся как есть
- `app/middleware/**`, `app/plugins/**`, `app/utils/**`
- `tests/unit`, `tests/integration`, `tests/api`

Если при переносе выясняется, что composable отдаёт данные в неудобной для нового UI форме — **меняем компонент, а не composable**. Правки в composables допустимы только там, где новый интерфейс требует поля, которого раньше не показывали; такие случаи фиксируются в журнале этапа.

`tests/e2e` переписывается вместе с UI — селекторы изменятся.

## 3. Ветка и режим работы

```
git checkout -b feat/frontend-rebuild
```

Ветка живёт до полного паритета по функциям. Мержится одним разом.

**Паритет обязателен.** Ни одна из 46 страниц не выпадает: половина переписанного приложения не мержится, а старый код в этой же ветке удаляется. Список страниц ведётся чек-листом в `design-preview/migration-checklist.md`, страница закрывается только после проверки в реальном приложении.

Макеты открываются локально по HTTP (`file://` заблокирован, рядом нужен `support.js`):

```
cd design-preview/catalog && python -m http.server 8791
```

## 5. Правила переноса макета в код

1. **Инлайн-стили превращаются в утилиты Tailwind.** В макетах все значения взяты из `var(--…)`, поэтому замена механическая: `background: var(--color-panel)` → `bg-panel`, `color: var(--color-text-muted)` → `text-muted`, `border-radius: var(--radius-md)` → `rounded-md`. Хардкодных цветов в макетах нет — если встретился, это ошибка макета, её фиксируем, а не переносим.
2. **Блоки `<!-- component: X -->` в макете — это границы будущих компонентов.** Имя из комментария сохраняется.
3. **Заглушки иконок заменяются настоящими.** У каждой стоит `<!-- icon: mingcute:… -->`; в проекте уже подключён `@nuxt/icon` в режиме `svg`, подстановка — одна строка.
4. **Пометки «заменяемая часть»** в эталонах списка и детали — это места, куда доменные разделы подставляют свои фильтры, колонки, действия и свойства.
5. **`support.js` и элемент `<x-dc>` в код не переносятся** — это рантайм среды макетов.
6. **Восемь состояний статуса** из системы — единственный источник правды. Существующие 15 badge-компонентов (`TrendStatusBadge`, `VideoStatusBadge`, `PipelineStatusBadge`, …) схлопываются в `UiStatusBadge` плюс доменный маппинг.

## 6. Этапы

Каждый этап заканчивается работающим приложением в ветке. Порядок обязателен: следующий этап опирается на предыдущий.

### Этап 0 — Фундамент

- `design-preview/_system/tokens.css` → `app/assets/css/main.css`
- Удалить DaisyUI из `main.css` и `package.json`, снять `@source inline(...)`
- Переключить `colorMode` в `nuxt.config.ts`: темы `dark` / `light` вместо пяти, `dataValue: "theme"` сохраняется, `data-accent` — отдельная настройка
- Проверка: `bun run dev` поднимается, приложение выглядит сломанным (это ожидаемо — DaisyUI-классы больше не работают)

### Этап 1 — Примитивы `ui/`

Собрать из `00-system.dc.html` весь состав `components/ui/`. Каждый примитив — со всеми состояниями из макета, включая фокус, отключённое, загрузку, ошибку.

Проверка: страница-витрина `app/pages/_ui.vue` (временная, удаляется перед мержем) визуально совпадает с `00-system.dc.html` в обеих темах.

### Этап 2 — Оболочка

`AppSidebar` + `AppTopbar` + `AppCommandPalette` + `AppPageHint`, `layouts/default.vue` переписан.

- Навигация строится из того же `canAccessModule` / `can`, что и сейчас; недоступные пункты не рендерятся
- Счётчики у пунктов: поллинг, `min-width` под 3 знака, без анимации
- Подсказка страницы переезжает из `SharedPageGuide` в кнопку «?» топбара, содержимое `app/utils/guides.ts` сохраняется
- Command palette: переходы по разделам, поиск сущностей, команды

Проверка: по всем разделам можно пройти, права работают, ⌘K открывается и ищет.

### Этап 3 — Эталон списка

`components/list/**` по `02-list-trends.dc.html`, обкатывается на `/trends`.

Включает: три класса сохранённых представлений (системные, общие, личные), фильтры в URL с кнопкой копирования ссылки, меню колонок с составом в представлении, массовые действия, drawer с навигацией по соседям, пагинация страницами + «Показать ещё».

Право `canManageSharedViews` добавляется в RBAC. Хранение представлений — новая таблица, миграцией.

Проверка: `/trends` работает целиком, 17 строк на 1440×900.

### Этап 4 — Эталон детали

`components/detail/**` по `03-detail-video.dc.html`, обкатывается на `/videos/[id]`.

Включает: липкую шапку с навигацией по соседям, степпер шагов, разбивку стоимости, гейт качества, отчёт об ошибке с выбором шага для повтора. Действия строк шагов разводятся по правилу «бесплатное и локальное — в строку, оплачиваемое — через меню с ценой»; `rerun-step`, `skip-step`, `rerender-assembly`, `edit-subtitles` уже есть в API.

Проверка: `/videos/[id]` работает целиком, включая живое обновление во время генерации.

### Этап 5 — Массовый перенос разделов

Оставшиеся ~44 страницы собираются из эталонов этапов 3 и 4. Это самый объёмный, но самый механический этап. Порядок — по частоте использования:

Тренды (готово) → Сценарии → Идеи → Видео → Загрузки → Аккаунты → Постинг → Персонажи → Сцены → Креативы → Промты → Прокси → Устройства → Google Drive → Референсы → Админ-разделы.

Каждая страница закрывается в чек-листе после проверки в приложении.

### Этап 6 — Сложные экраны

Не собираются из эталонов, переносятся отдельно:

- Редактор конвейера (`04-pipeline-editor.dc.html`) — Vue Flow остаётся, меняется оформление нод, палитры, панели. Раскладка графа разводится на три случая: «Выровнять по сетке» на канвасе, «Разложить по слоям» в меню через историю undo, автораскладка нод без координат при загрузке с пометкой `isDirty`.
- Монитор запуска (`05-run-monitor.dc.html`)
- Аккаунты и очередь публикаций (`06-accounts-queue.dc.html`) — почасовая кривая восстановления лимита считается по нашей истории публикаций и подписывается как прогноз; агрегат от `content_publishing_limit` главнее
- Аналитика (`07-analytics.dc.html`) — атрибуция по первому и последнему касанию, цепочка собирается через `messengerUserId` в `AttributionEvent`
- Дашборд (`01-dashboard.dc.html`)
- Настройки и админка (`08-settings-admin.dc.html`)

## 7. Критерии приёмки

- Ни одного класса DaisyUI в `app/`
- Все 46 страниц открываются и выполняют то же, что раньше
- Обе темы корректны, контраст текста ≥ 4.5:1, нетекстовых элементов ≥ 3:1
- На 1440×900 в списке помещается не менее 15 строк
- Полная клавиатурная проходимость, видимый фокус
- 1440 / 1024 / 390 без горизонтального скролла страницы
- `bun run test` и `bun run test:e2e` зелёные
- При поллинге раз в 5 секунд вёрстка не дёргается и списки не перескакивают под курсором

## 8. Журнал отступлений

Здесь фиксируется всё, что сделано иначе, чем в макетах или в этой спецификации.

**Этап 0**

- `PipelineCanvas` брал цвет обводки захардкоженным `oklch(...)` с пометкой «приблизительно». Заменён на `var(--color-warning)` — в светлой теме прежнее значение было бы нечитаемым.
- `bun install` не выполнялся: Bun отсутствует в PATH, а `AGENTS.md` запрещает ставить его или переходить на npm без разрешения. `daisyui` убран из `package.json`, но остаётся в `node_modules`; `bun.lock` нужно обновить перед мержем.

**Этап 1**

- **Алиасы токенов.** Tailwind строит имя утилиты из полного имени токена, поэтому `--color-text-muted` дал бы класс `text-text-muted`. В `main.css` добавлен блок `@theme` с алиасами `--color-fg/muted/subtle/inverse` через `var()`. Исходные токены не переименованы — они остаются контрактом с макетами.
- **Зазор между колонками таблицы.** В макете грид без `gap`, и при узких колонках соседние заголовки слипаются («ВИРАЛЬНОСТЬСТАТУС»). В `UiTableHead` и `UiTableRow` добавлен `gap-x-3`.
- **`useToast` расширен.** Добавлено необязательное действие в тосте и хелпер `undoable`. Без этого нельзя выполнить требование «обратимые действия не спрашивают подтверждение, вместо него тост с «Отменить»». Существующий API не сломан.
- **Витрина `/_ui`.** Временная страница для сверки с `00-system.dc.html`. В `auth.global.ts` добавлено исключение, действующее **только при `import.meta.dev`**. Страница и исключение удаляются в этапе 7.

**Этап 2**

- **Счётчики в сайдбаре пока пустые.** Форма зафиксирована в `useNavCounters`, но агрегирующего endpoint нет: дёргать шесть списков поллингом раз в 5 секунд ради цифр в меню дороже, чем они стоят. Значения приедут вместе с `/api/dashboard/summary` в этапе 6 — дашборд считает ровно те же величины. До тех пор счётчик не рисуется: пустое место лучше выдуманного числа.
  **Закрыто в этапе 6.** `/api/dashboard/summary` появился вместе с дашбордом, счётчики в сайдбаре считаются им и работают.
- **Поиск по сущностям в ⌘K не подключён.** Разделы и команды работают, поиск по `vid_10842` и `@zavod.mebel.ru` требует общего серверного endpoint. Секция подключается в этапе 5 без изменения компонента.
  **Закрыто.** `/api/search` заведён, ⌘K ищет сущности.
- **Пункт «Запуски» под конвейером убран.** Общего экрана `/pipeline/runs` не существует — история живёт по `/pipeline/[id]/runs`. Ссылка попала бы в `pipeline/[id]` с `id="runs"`. Возвращается вместе с монитором запусков в этапе 6.
  **Закрыто в этапе 6, запуски.** Экран `/pipeline/runs` заведён, пункт вернулся. Статический маршрут перекрывает `pipeline/[id]`, в редактор с `id="runs"` не уводит.
- **Витрина `/_shell`.** Вторая временная страница: продуктовые страницы за авторизацией, а оболочку надо смотреть отдельно. Исключение в `auth.global.ts` расширено с `/_ui` до префикса `/_`, по-прежнему только при `import.meta.dev`.
- `SharedPageGuide` больше не используется в оболочке — содержимое `app/utils/guides.ts` показывает `AppPageHint` из кнопки «?». Сам компонент удаляется в этапе 5 вместе со страницами, которые его ещё зовут.

**Этап 3**

- **Право `canManageSharedViews` не заводилось.** Реальные флаги пользователя приходят из MarketingCamp при логине (`server/utils/rbac-presets.ts`), девятый флаг оттуда не придёт — новая колонка навсегда осталась бы в значении по умолчанию, то есть общие представления не смог бы вести никто. Гейт временно `canAdmin`, проверка в одном месте — `canManageSharedViews()` в `server/utils/saved-views.ts`. Когда MC научится отдавать отдельный флаг, меняется только эта функция.
- **Миграция `20260806090000_add_saved_views` не применялась.** `DATABASE_URL` в `.env` отсутствует, тестовая база на `localhost:5436` не поднята. SQL написан руками по конвенции проекта (остальные миграции здесь тоже рукописные), схема обновлена, Prisma Client перегенерирован. Перед использованием раздела миграцию нужно применить и проверить.
- **Закрепление вида по умолчанию — в localStorage.** Это личная настройка одного человека на раздел; отдельная таблица ради одной строки не нужна.
- **`/trends` проверена на живой базе.** Миграция применена, таблица `SavedView` существует. Через dev-сессию прогнан весь путь: `POST /api/saved-views` создаёт представление и нормализатор действительно выбрасывает пустые значения и вложенные объекты, `DELETE` возвращает 404 на несуществующее и 400 на мусорный идентификатор, `GET /trends` отдаёт SSR с оболочкой, системными представлениями, личным представлением **из базы** и пустым состоянием. Классов DaisyUI в разметке нет.
- **Кодировка не сломана.** Кириллица в имени представления сначала выглядела битой, но проверка кодпойнтов прямо в Postgres показала: портит её оболочка Windows при передаче аргументом `-d`, а не приложение. Отправленное файлом хранится как `U+412 U+44B U+441`.
- **Табы «Профили парсинга» и «Запуски» на `/trends` пока на старых компонентах** и выглядят несогласованно. Переносятся в этапах 5 и 6.
  **Закрыто в этапе 6, тренды.** Обе вкладки и шесть компонентов переписаны.
- `perPage` в сторе трендов стал настраиваемым (25/50/100 вместо зашитых 20), сортировка по умолчанию — `-importedAt`.

**Этап 4**

- **Компоненты детали готовы, страница `/videos/[id]` к ним ещё не подключена.** Сделаны `DetailHeader`, `DetailRelations`, `DetailStepRow`, `DetailCostBreakdown`, `DetailErrorReport`, `DetailQualityGate`, `DetailVariantStrip` и маппер статусов видео. Все проверены на витрине `/_ui`. Сама страница — 500 строк со своей логикой опроса прогресса, вариантов и субтитров; её перенос сделан отдельным шагом, чтобы не смешивать создание эталона с разбором legacy-разметки.
- **Правило действий у шага реализовано данными, а не догадкой**: `VIDEO_STEP_IS_CHEAP` в `app/components/video/VideoStatusMap.ts`. Сейчас дешёвая только сборка; остальные шаги дёргают Replicate и уходят в меню с ценой. Эндпоинты под это уже есть: `rerun-step`, `skip-step`, `rerender-assembly`, `edit-subtitles`.
- **`/videos/[id]` подключена к эталону и проверена вживую** на трёх состояниях: готово, упало, идёт прямо сейчас. Проверены вкладки, меню платного шага с подтверждением суммы, навигация по соседям, обе темы, 1440 и 390 без горизонтального скролла. Данные для проверки создаёт `scripts/seed-videos-demo.ts` — по образцу существующего `seed-admin-logs-demo`, только тестовая БД.
- **`DetailStepRow` переразмечен сеткой.** На витрине он выглядел правильно, а на реальных названиях («Генерация клипов» рядом с длительностью, попыткой и суммой) подпись схлопывалась до одной буквы. Модель и длительность ушли второй строкой, как в макете; сумма и меню — отдельными колонками.
- **`DetailErrorReport` получил `cancellable`.** Кнопка «Отменить» на уже упавшем запуске отменять нечего — показывается только когда генерация идёт.
- **Навигация по соседям опирается на загруженную страницу списка** (стор фильтров раздела). Если ролика в ней нет — прямой ссылкой или после смены фильтров — стрелки отключены и позиция не показывается: соседей мы не знаем, а прыгать на первый элемент списка хуже, чем не прыгать никуда.
- **Три компонента расходились при гидратации.** `AppCommandPalette`, `UiToastContainer` и `VideoUniqueVariantsSection` телепортируются в `body` (последний ещё и тянет данные только на клиенте). Vue бросал поддерево недорисованным — секция уникализации показывала одни вкладки без содержимого. Все три обёрнуты в `ClientOnly`.
- **Заглушка пропавшего кадра рисуется в компоненте.** Общая `onAssetMissing` из `app/utils/image-fallback.ts` подставляет светлую картинку с зашитыми `#e5e7eb`/`#9ca3af`; в тёмной теме это яркое пятно. **Этап 6, аккаунты и очередь публикаций**

- **Лимита публикаций в интерфейсе нет, и это не забывчивость.** Макет строит вокруг него половину экрана: свободная ёмкость на сутки, колонка «34 / 50», почасовая кривая восстановления, подпись «полностью к 17:12». Величину отдаёт только Instagram и только в момент отправки — `getPublishingLimit` в `server/utils/social/instagram-api.ts` зовётся из адаптера публикации, в базу не пишется и ни в один endpoint не выведена. Считать её по своей истории — выдумывать число, поэтому колонка, плитка ёмкости и подписи восстановления убраны целиком. Появятся вместе с полем в API.
- **Отметки готовности собраны из своих данных.** В макете это токен, права, профиль и прогрев. Прав на публикацию платформа нам не отдаёт, прогрев живёт в `/api/admin/accounts-health` и виден на своей странице. В строке — токен, стиль-профиль, прокси и устройство; последние две у аккаунтов на официальном API рисуются пунктиром «не требуется». Вычисление — `AccountReadinessMap.ts`, рядом с компонентами.
- **Сортировки и постраничной выдачи у аккаунтов нет** — `/api/accounts` принимает только `appId`, `platform` и `status`. Поиск по названию и отбор «требуют внимания» считаются по загруженному списку, позиция в панели деталей — тоже.
- **Массового выделения в списке аккаунтов нет.** В макете чекбоксы обслуживают распределение роликов, а его место — очередь публикаций. Единственная массовая операция над аккаунтами — отключение, и делать её пачкой опаснее, чем полезно.
- **Календарь очереди — сетка «аккаунт × час» без свободной ёмкости.** Клетка показывает, сколько задач стоит в этом часу, и красится по самому тревожному состоянию внутри. Перетаскивания нет: `PATCH /api/posting-jobs/:id` время менять умеет, но час — слишком грубый шаг для минимального интервала между публикациями, время правится в карточке. Задачи вне окна посчитаны отдельной подписью.
- **Карта унаследованных зон читается через `useFetch`.** `loadLegacyModules()` не ждёт ответа: сервер рисовал страницу с выключенной зоной, клиент — с включённой, и Vue бросал поддерево при гидратации. Composable не тронут — страница заполняет его общее состояние сама.
- **Цвета платформ вынесены в `app/components/ui/platform-meta.ts`.** Строки списков показывают ту же цветную метку, что и `UiPlatformBadge`, а второй копии фирменных значений в коде быть не должно. Это по-прежнему единственное место с небрендовыми цветами.
- **Пачки аккаунтов теперь можно создавать.** `POST /api/account-groups` существовал, а кнопки не было: пачку заводили только на карточке приложения, своей формой, дублировавшей модалку правки. Осталась одна модалка на оба пути, и в ней появился режим раздачи — он менял число публикаций из одного ролика, но был не виден.
- **Четыре компонента не резолвились по имени.** `AccountIndigoTab` (файл `AccountDeviceTab.vue`) — вкладка устройства была пустой; `DeepCheckHistoryModal` в `components/account` — история проверок не открывалась; `AccountsHealthSummary`, `AccountsHealthByPlatform` и `AccountsHealthTable` на `/admin/accounts-health` — страница не рисовала ни одного блока. Первый переименован в шаблоне, второй — в файле, остальные получили префикс `Admin`.
- **`seed-devices-demo` клал адрес и доступы прокси открытым текстом.** DTO списка прокси их расшифровывает, поэтому `GET /api/proxies` падал с «Неверный формат зашифрованных данных» — при включённой зоне не работали ни страница прокси, ни вкладка прокси у аккаунта. Сид чинён, существующие строки тестовой базы перешифрованы.
- **Пять иконок не существовали** и молча не рисовались: `mingcute:refresh-line` (кнопка проверки входа), `image-line` (заглушка кадра в списке постов), `scroll-line` (шаг скролла в плане прогрева), `magic-line` (кнопка рекомендаций стиля), `user-following-line` (плитка подписчиков).
- **`confirm()` заменён модалкой** в отвязке профиля устройства и в отмене с удалением сессии прогрева.
- **Демо-данные.** `seed-accounts-demo` расширен до шести аккаунтов (истекающий токен, истёкший, отозванный, стиль-профили, пачка) — на трёх активных проверять нечего. Добавлен `seed-posting-jobs-demo`: очередь во всех состояниях, часть расставлена по ближайшим суткам для сетки.

**Этап 6, дашборд**

- **Половина макета не перенесена, потому что величин нет.** Из строки состояния убраны расход за сутки и состояние интеграций, целиком убраны воронка со средним временем шага и результаты за период. `/api/dashboard/summary` считает шесть счётчиков и очередь причин, и это всё, что есть; расход по дням живёт в админских балансах и виден не всем.
  **Расход за сутки вернулся** вместе с журналом списаний (см. «Этап 6, деньги»): сводка отдаёт `spend` тем, у кого есть `canAdmin`, остальным `null` — и плитка не рисуется вовсе, по тому же правилу, что и счётчики недоступных разделов. Число плиток в строке стало переменным, поэтому колонок ровно столько, сколько плиток. Состояние интеграций, воронка и результаты за период по-прежнему не перенесены.
- **Плитки строятся из тех же счётчиков, что и сайдбар.** Разделы без доступа не считаются на сервере и не рисуются в строке — счётчик не должен подсказывать объём того, чего человек не видит.
- **У строки очереди нет разбора причины.** В макете под заголовком идёт вторая строка вида «2 × lip-sync, 1 × таймаут»; сводка отдаёт количество и возраст, но не состав. Строка показывает то, что известно: причину, число, возраст старшего и действие.
- **Запуски в работе тянутся своим запросом к `/api/pipelines/monitor`.** Стор монитора держит поиск и фильтры страницы конвейеров; делить его с дашбордом значит связать состояния двух экранов. Процента выполнения нет: сводка отдаёт текущий шаг и число пройденных, а общее число шагов знает только конвейер запуска.
- **`useTrendStats` осталась без потребителей** — старый дашборд был единственным. Composable не удаляли: он вне границ переноса.

**Этап 6, монитор запусков**

- **Стоимости запуска нет ни у запуска, ни у шага.** Макет ставит сумму в строку шага, в шапку, в карточку списка и в диаграмму. В `WorkflowRun` и `WorkflowStep` полей стоимости не существует, агрегата по запуску не отдаёт ни один endpoint. Все суммы убраны; колонка стоимости в строке шага заменена числом попыток — это реальные данные (`attemptCount` и `retryPolicy.maxRetries`) и они объясняют, почему шаг шёл долго. Единственные деньги, которые видны, — фактическая стоимость роликов из `output.videos[].totalCostActual` в разборе шага «Видео»: их туда кладёт исполнитель.
  **Закрыто в этапе 6, деньги.** Поля появились, суммы вернулись в строку шага (колонка попыток осталась рядом), в шапку и в карточку списка. Диаграмма длительностей сумм не показывает — там сравниваются времена, и вторая ось чисел мешала бы.
- **Кто запустил — не показываем.** `triggeredBy` хранит id пользователя, endpoint запуска его не резолвит и объединения с `ZavodUser` не делает. Вместо имени в шапке стоит способ запуска: вручную, расписание, вебхук.
  **Закрыто в этапе 6, запуски.** Резолв добавлен в список и в деталь, в шапке стоит «Д. Кузнецов, вручную». Без автора (расписание, вебхук) остаётся один способ запуска.
- **Общего экрана «все запуски» не появилось**, и пункт «Запуски» в сайдбаре не вернулся, хотя этап 2 обещал вернуть его здесь. Endpoint, отдающего запуски по всем конвейерам, нет: `/api/pipelines/monitor` отдаёт конвейеры с вложенными запусками, а не плоский список. Заводить его — серверная работа, а она вне границ переноса. История живёт по `/pipeline/[id]/runs`, ссылка на неё есть в блоке «Исполнения» и в шапке монитора.
  **Закрыто в этапе 6, запуски.** `/api/pipelines/runs` и экран `/pipeline/runs`.
- **Шаги упорядочены графом, а не временем создания.** Движок заводит строку шага заранее, и сортировка `createdAt asc` из endpoint ставила «в очереди» выше уже выполненных: на живых данных первыми шли «Аналитика» и «Публикация». Порядок считает `PipelineGraphOrder.ts` обходом в ширину от блоков без входящих связей; он же даёт порядок схеме справа и число блоков для «шагов N из M». Берётся `graphSnapshot` запуска, а не текущий граф конвейера — его с тех пор могли перерисовать.
- **Три места ломались на SSR, и это была настоящая поломка, а не косметика.** Watcher на сервере не срабатывает: накопление страниц списка запусков через `watch(data)` оставляло левую колонку пустой в SSR и заполняло её после гидратации, Vue бросал поддерево. То же с авто-раскрытием упавшего шага. Оба переведены на `computed` от данных. Всё, что зависит от «сейчас», вынесено в `PipelineMonitorLiveDuration`: завершённое считается из дат и рисуется на сервере, незавершённое уходит в `ClientOnly`. «Сегодня»/«Вчера» в заголовках дней — тоже `ClientOnly`, группировка при этом остаётся серверной.
- **«Пропустить и продолжить» из макета не нарисовано.** У шагов конвейера такого endpoint нет: движок умеет только `retry-step`, и он переисполняет всё ниже по графу. Повтор шага доступен лишь на упавшем или остановленном запуске — это ограничение движка, а не интерфейса.
  **Закрыто в этапе 6, запуски.** Заведён `skip-step`, кнопка вернулась.
- **«Настройки ноды» стали «Открыть в редакторе».** Редактор конвейера не читает ноду из адреса, глубокой ссылки на блок не существует.
- **Логи собраны из шагов.** Отдельного потока нет — строки лежат в `step.logs` и приезжают тем же опросом, что и запуск. Поэтому в подвале «показано N из M», а не «поток открыт · 1 284 строки», как в макете. Фильтр по уровню, поиск, привязка к шагу и автопрокрутка работают.
- **У диаграммы длительностей нет «нормы».** Макет красит шаг, который «дольше нормы в 3+ раза»; истории длительностей по типам блоков не хранит никто. Порог считается от самого запуска: больше половины его времени — предупреждение. Легенда так и подписана.
  **Закрыто в этапе 6, запуски.** Норма — медиана длительности успешных шагов этого типа за две недели (`/api/pipelines/step-norms`). Запасной порог от запуска остался для типов, по которым наблюдений не набралось.
- **Категорийные токены `--color-cat-*` добавлены в `main.css`.** В `_system/tokens.css` их нет — они объявлены только в макетах 04 и 05, то есть это язык канваса конвейера, а не всей системы. Схема запуска рисует ими полоску принадлежности слева; статус блока по-прежнему передаётся рамкой из общего словаря.
- **Мапперы рядом с компонентами**: `PipelineRunStatusMap.ts` (статусы запуска и шага к восьми состояниям, доменные подписи), `PipelineNodeMeta.ts` (подпись, иконка и категория блока), `PipelineGraphOrder.ts` (порядок обхода), `PipelineRunFormat.ts` (длительности «4 м 26 с» — `shared/utils/pipeline-format` отдаёт «4.4мин», а в мониторе шаги сравнивают между собой).
- **Платное разведено по правилу с одной оговоркой.** «Повторить запуск» и «Повторить с упавшего шага» — в меню шапки с пометкой «платно»; суммы у пометки нет, потому что её неоткуда взять, и подтверждение объясняет это словами. **Сумма появилась**: «около N $» — во что запуск обошёлся в прошлый раз, а у повтора с шага — сумма этого шага и всего ниже по графу. Это оценка, а не счёт: граф и цены провайдеров могли поменяться, поэтому «около». «Остановить» и «Запустить» остались видимыми кнопками с подтверждением — тот же компромисс, что у включения устройства: это главные действия раздела.
- **Четыре модалки конвейера переписаны** с нативного `<dialog>` на `UiModal`: создание, шаблоны, импорт, предпросмотр. Форма оформления (имя, описания, иконка, цвет, теги) вынесена в `PipelineMetaForm` — в предпросмотре она занимала больше половины файла. Удаление со словом-подтверждением тоже переехало на `UiModal` и открывается поверх предпросмотра.
- **`mingcute:cpu-line` заменена на `server-line`** в блоке «Исполнения» — прежней в наборе не существует.
- **Отбор «только упавшие» считается по загруженным страницам.** Endpoint принимает `status`, но `usePipelineRuns` его не передаёт, а composables вне границ переноса. Счётчик рядом с кнопкой честно показывает число упавших среди загруженного.
  **Закрыто в этапе 6, запуски.** Отбор ушёл на сервер, счётчик берётся из меты.
- **`PipelineMonitorRunSteps` удалён.** Строка запуска в блоке «Исполнения» раскрывала шаги вторым запросом; теперь она ведёт на монитор, где то же самое показано целиком. Замена проверена вживую до удаления.
- **Демо-данные `scripts/seed-pipeline-runs-demo.ts`**: конвейер с графом из девяти блоков и восемь запусков — идущий с упавшим некритичным шагом, успешный, упавший на гейте, остановленный человеком, без данных, ждущий очереди и два вчерашних. У шагов есть логи, входы, выходы, попытки и категории ошибок.
- **Подписи `renderStatus` сверены с исполнителем.** `rendered_ok` действительно значит «отправлено» (`result.sent === true` в `server/utils/pipeline-executors.ts`), а не «шаблон собран»; добавлено недостающее состояние `blocked_no_data`.

**Этап 6, настройки и админка**

- **Ключей сервисов в интерфейсе нет и не будет.** Макет строит страницу интеграций вокруг карточки с полем «API-ключ», маской и кнопкой «Заменить». Ключи задаются переменными окружения, в базе их нет, и endpoint, который их читает или пишет, отсутствует. Форма с маской по несуществующему полю — обман. Страница вместо неё отвечает на вопрос, который у оператора на самом деле есть: где что настраивается и где видно, что оно работает. Кнопки «Проверить все» тоже нет — проверять нечем.
  **Кнопка «Проверить все» появилась в этапе 6, админка.** Ключей на экране по-прежнему нет: проверка отвечает «отвечает / не отвечает / не настроен / мок-режим», а само значение ключа наружу не выходит.
- **Матрицы прав из макета нет.** Права приходят из MarketingCamp при логине (`server/utils/rbac-presets.ts`) и в ContentFactory только читаются. Матрица с чекбоксами обещала бы правку, которой не существует; список пользователей с ролями живёт на `/admin/users` и остаётся только на просмотр.
- **Переключателей модулей и «опасного действия с вводом названия» нет по той же причине.** `moduleAccess` приходит извне, а карта унаследованных зон читается из окружения — выключить зону кнопкой нельзя. Страница интеграций пишет, какой флаг включает зону, и показывает её текущее состояние.
- **Разбивки расхода по типам операций нет.** `/api/admin/balances` отдаёт остатки по сервисам, а не траты по операциям; «Итого за сутки» и «290 ₽ за ролик» из макета собирать не из чего. Прогноз «хватит на N дней» показывается только там, где сервер посчитал `burnRate` — свой расчёт по чужим числам был бы выдумкой.
  **Закрыто в этапе 6, деньги.** `/api/admin/spend` считает разбивку по журналу списаний, панель вернулась на страницу балансов вместе с итогом и стоимостью ролика.

Endpoint отдаёт другое: сколько роликов проверено и у скольких пропали файлы; `freeSpaceGB` приходит без общего объёма, и процента из него не выйдет. Полоски показывают долю найденных файлов, кадров и клипов.
  **Заполненность добавлена в этапе 6, админка.** `statfs` отдаёт и свободные блоки, и общее число — процент считается из них, а не выдумывается. Целостность осталась: это разные вопросы, и оба нужны.
- **`useFetch` с `server: false` снова потребовал `ClientOnly`.** У `admin/storage-health` данные грузятся только в браузере, и без обёртки на сервере страница вечно в загрузке. Заодно всплыло, что `pending` на сервере `false`, а в браузере сразу `true`: привязка к кнопке «Проверить заново» ломала гидратацию — у кнопки теперь своё состояние повтора.

- **Telegram перенесён наполовину, и это записано в чек-листе.** Страница, вкладки и «Обзор» — новые; шесть вкладок в `app/components/admin/telegram/` (диагностика, шаблоны, ключи, чаты, доставки, аудит) остаются на DaisyUI. Это 2 300 строк, и мешать их в один заход с шестью другими страницами значит не проверить ни одну.

**Этап 6, админка (серверная часть)**

- **Состояние интеграций появилось, ключи — нет.** `server/utils/integrations/health.ts` дёргает у каждого сервиса endpoint, который не тарифицируется и не расходует токены: `/v1/models` у Anthropic, `/v1/account` у Replicate, `getMe` у Telegram, `users/me` у Apify. Генерации в проверке нет и быть не может — иначе «Проверить все» стоило бы денег. Само значение ключа наружу не выходит: наверх идут только «отвечает», «ключ отклонён», «не настроен» и «мок-режим».
- **Мок-режим — отдельное состояние, а не «работает».** На стенде все ключи заглушены, и зелёная галочка там означала бы неправду. Проверка так и пишет: обращений наружу не было, настоящий ключ не проверялся.
- **Реестр фоновых задач.** `server/utils/scheduler-registry.ts` — кто запущен, когда был последний тик, что упало. Самая частая авария завода выглядит не как ошибка, а как тишина: планировщик перестал тикать, и очередь просто не разбирается. Состояние в памяти процесса, как и `getRuntimeStats`: приложение живёт в одном экземпляре, и писать тик в базу раз в тридцать секунд ради строки в интерфейсе незачем. Просроченной задача считается после двух интервалов — один пропущенный это нормальный дрейф таймера под нагрузкой.
- **Ошибка тика не отменяет сам тик.** Задача жива, но её работа не удалась — это разные аварии, и в панели они выглядят по-разному.
- **Аудит действий людей не стал новой таблицей.** Макет помечает такие записи отдельно; почти все они уже несут `userId` — в деталях записи агента, в журнале доступа к секретам, в журнале AI. `admin-log-aggregator` выводит признак из него и не выдумывает; заводить пятую таблицу ради флага, который уже лежит в четырёх, — работа без результата.
- **Матрица прав, переключатели модулей и правила уведомлений по-прежнему не сделаны** — по прежним причинам: права приходят из MarketingCamp только на чтение, `moduleAccess` и карта унаследованных зон приходят извне, а сущности «правило уведомления» в схеме не существует.
- **Демо-данные `scripts/seed-telegram-demo.ts`**: четыре чата (в том числе неподтверждённый и с выключенными уведомлениями), три шаблона, три ключа, пять доставок и пять записей аудита. Один шаблон намеренно с переменной не из реестра — иначе не видно разбор предупреждения.

**Этап 6, метрики публикаций**

- **Доли выводились как проценты, и на пустой базе этого не было видно.** `watchThrough` и `ctr` хранятся долей 0…1 — так их отдают платформы и так они называются (доля досмотра, click-through *rate*), — а интерфейс дописывал к доле знак процента: 0,703 показывалось как «0.703%» вместо «70,3 %». Нашлось сразу, как в базе появились замеры. Масштаб теперь записан в `MetricsResult`, форматирование — в `app/components/analytics/AnalyticsFormat.ts`.
- **Демо-замеры выведены из «характера» ролика**, а не набраны случайно: у виральной публикации высокий досмотр и много репостов, у провальной — низкий досмотр и почти нет реакций. Случайные числа дают ролик с 40 000 просмотров и нулём лайков, и любые выводы по такому экрану бессмысленны.
- **История обрывается там же, где на живом заводе.** Замеров из будущего не бывает: у публикации, вышедшей час назад, в истории одна точка. `seed-uploads-demo` расширен — каждая третья фоновая публикация теперь опубликованная и вышла несколько дней назад, иначе сравнивать площадки и считать динамику не на чем.
- **Перенос макета 07 не сделан.** Данные под него есть, страница и девять компонентов — нет; они остаются на DaisyUI. Это следующий заход, и мешать его с заведением данных значит не проверить ни то, ни другое.

**Этап 6, тренды: профили парсинга и запуски**

- **Вкладка выбирается адресом**, а не только состоянием: `?tab=profiles` и `?tab=runs`. Ссылку на профили дают в чате, и она должна открывать профили.
- **Статусы парсинга не схлопнуты в общий словарь.** У прогона четыре разных «выполняется» — Apify собирает, идёт импорт, идёт анализ, — и по ним оператор понимает, сколько ещё ждать. `TrendRunStatusBadge` берёт из словаря только тон; подписи в `TrendRunStatusMap.ts`. Там же состояние проверки конфигурации: «не проверен» — это не «черновик» и не «ошибка», а отсутствие знания, и запуск при нём разрешён.
- **Запуск парсинга остался видимой кнопкой**, хотя он платный: Apify тарифицирует прогон. Тот же компромисс, что у включения устройства — цена стоит прямо на кнопке («Запустить · платно»), а подтверждение объясняет, что платится за собранные элементы, поэтому остановка на середине денег не вернёт.
- **Проверка конфигурации уехала в меню.** Она бесплатна, но нужна раз в жизни профиля, а в строке отбирала место у запуска. В карточке со сломанным конфигом остаётся своя ссылка «Проверить снова» прямо в тексте ошибки — там она к месту.
- **`overflow-hidden` с карточки снят.** Меню действий выпадает вниз и обрезалось нижней границей карточки: видно было три пункта из шести.
- **Три места ломались на гидратации.** `useTrendwatcherActiveRuns`, `useTrendwatcherRunHistory` и `useTrendwatcherRunDetail` ходят с `server: false`. Вкладка «Запуски», плашка «парсинг идёт» и счётчик у вкладки обёрнуты в `ClientOnly`; карточки профилей рисуются на сервере, поэтому признак «идёт прямо сейчас» им передаётся только после монтирования. Composables не тронуты.
- **`confirm()` заменён модалками** у удаления профиля, запуска парсинга и отмены прогона.
- **`TrendFilters.vue` удалён.** Его никто не звал с тех пор, как фильтры переехали в `TrendListView` эталона списка.
- **Демо-данные `scripts/seed-trend-profiles-demo.ts`**: пять профилей — работающий прямо сейчас, с расписанием, выключенный со сломанным актором, на три площадки и ни разу не запускавшийся; у прогонов логи, шаги, категории ошибок и диагностика Apify. Без них обе вкладки показывали пустое состояние, и проверять было нечего.

**Этап 6, деньги (серверная часть)**

С этого раздела спецификация перестаёт запрещать `server/**`: из макетов было вырезано много элементов не по вкусу, а потому что величин не существовало. Серверные изменения идут отдельными коммитами от переноса интерфейса.

- **Стоимость живёт на шаге, агрегат — на запуске.** Миграция `20260806120000_add_workflow_run_cost` добавляет `costActual` и `costEstimate` в `WorkflowStep` и `WorkflowRun`. Агрегат денормализованный, но пересчитывается из строк шагов (`recalcRunCost` в `server/utils/pipeline-cost.ts`), а не копится в памяти: запуск переживает рестарт и resume, а пересчёт идемпотентен. `retry-step` зовёт его после удаления шагов — иначе в шапке висела бы сумма вместе с уже стёртыми шагами.
- **Контракт с исполнителями — служебные ключи output**, `_costActualUsd` и `_costEstimateUsd`, по образцу `_noData` и `_domainDegraded`. Их кладёт тот, кто знает сумму: сейчас это `executeVideoNode`, который складывает `videos[].totalCostActual` — ролик сам сложил свои шаги при завершении, считать заново нечего. Движок ключи только снимает и не знает про форму output конкретной ноды.
- **Ноль и «неизвестно» — разные вещи.** У логических блоков (`filter`, `set`, `if_switch`, `loop`, `wait`, `note`, `notification`) стоит честный ноль: они ничего не тратят, и прочерк на них заставлял бы гадать, где сумма не посчитана. `code` и `http_request` ходят наружу, и во что это обходится, знает только автор конвейера — у них прочерк.
- **У упавшего и отменённого шага суммы нет.** Исполнитель бросает исключение, output не возвращается, а сколько провайдер успел списать до отказа — мы не знаем. Записывать сюда ноль значило бы утверждать, что неудачная попытка бесплатна, а это неправда.
- **Ноль на идущем запуске не показывается.** Пока запуск идёт, агрегат равен сумме уже отчитавшихся шагов; если платные ещё не завершились, получается ноль, который читается как «бесплатно». `runCostLabel` в `PipelineRunFormat.ts` прячет ноль у незавершённого запуска и показывает у завершённого — там это уже сообщение.
- **Расход по типам операций считается по журналу списаний**, а не по агрегату шагов: `AiAuditLog` (`action='external_api_call'`) хранит те же деньги, но с точностью до шага ролика, а `WorkflowStep.costActual` — только до блока конвейера. Модуль `server/utils/balance/spend-breakdown.ts`, endpoint `/api/admin/spend` с правом `canAdmin` — тем же, что у балансов.
- **Группы операций собраны по реальным ключам шагов**, а не по подписям макета: «Lip-sync и видео», «Синтез речи и музыка», «Сценарии и критик», «Рендер». Строка рендера всегда ноль — сборка идёт локальным ffmpeg, — и оставлена намеренно: оператор спрашивает «а сборка сколько стоит», и постоянный ноль отвечает лучше, чем отсутствие строки. «Прочее» появляется, только если туда что-то попало.
- **Валюта одна на всё приложение — доллар.** Учёт завода в USD (`ServiceBalanceEntry.currency`, `AiAuditLog.costUsd`, `Video.totalCostActual`), а перенесённые из legacy экраны рисовали те же числа с рублём. Общий `shared/utils/money.ts` форматирует руками, а не через `Intl`: сервер и браузер расходятся в пробеле-разделителе, и Vue бросает поддерево при гидратации. Знак заменён во всех местах, где показывается та же величина: разбивка стоимости, строка шага ролика, отчёт об ошибке, список роликов, полоса вариантов, панель шагов.
- **Три сида.** `seed-cost-ledger-demo` не выдумывает суммы: раскладывает уже существующие `VideoGenerationStep.actualCost` в журнал списаний ровно так, как это делает `logStepCost` на живом заводе, и проставляет роликам время завершения — без него панель не на что делить. `seed-pipeline-runs-demo` считает стоимость шагов той же функцией, что и движок. `seed-dev-user` заводит учётку стенда и приложение: раньше строка создавалась руками и пропадала после первого прогона DB-тестов (`TRUNCATE` всей схемы), после чего стенд нельзя было открыть вообще.

**Этап 6, запуски (серверная часть)**

- **Один модуль на два списка.** `server/utils/pipeline-run-list.ts` обслуживает и историю одного конвейера, и общий экран: разница только в наборе конвейеров, а фильтры, сортировка, состав полей и мета одинаковые. Разъезжаться им нельзя — это один и тот же список в двух местах интерфейса.
- **Мета отдаёт разбивку по статусам**, а не только общее число, и считается БЕЗ фильтра по статусу: иначе «4 упало» исчезало бы ровно в тот момент, когда включён отбор упавших. Отбор «только упавшие» ушёл на сервер, счётчик у кнопки берётся из меты.
- **Число блоков считает Postgres.** `jsonb_array_length` по снимку графа отдельным запросом: тащить `graphSnapshot` в список из двадцати строк — это сотни килобайт JSON ради одного числа на строку. Снимок берётся у запуска, а не у конвейера: граф могли перерисовать, и «шагов 8 из 12» по текущему графу было бы ложью.
- **«Пропустить и продолжить» опирается на семантику resume, которая у движка уже была.** Шаг переводится в `skipped`, и `executePipeline` считает его выполненным через `completedNodeIds`, отдавая downstream пустой вход — так же, как если бы исполнитель вернул `null`. Downstream не сбрасывается: пропуск это «идём дальше», а не «переигрываем ветку». Ошибка шага не стирается — почему его пропустили, видно в разборе. Стоимость не обнуляется: если шаг успел списать деньги до отказа, мы этого не знаем.
- **Норма длительности — медиана, а не среднее.** Один зависший шаг на сорок минут сдвигает среднее так, что «дольше нормы» перестаёт срабатывать вообще. Типы блоков с числом наблюдений меньше пяти нормы не получают: по двум замерам норму не строят, и диаграмма для них падает на прежний порог «больше половины запуска».
- **Прогресс запуска — блоков пройдено из блоков графа.** Точнее не выйдет: движок заводит строку шага в момент начала обработки, поэтому идущий блок уже посчитан. Это «сколько блоков затронуто», и подпись такая же — «блоков N из M», а не «N% выполнено».
- **Прогресса внутри шага нет.** Макет обещает «обработано 6 из 14, осталось ~9 м». Общего поля прогресса у шага не существует, а разрозненные счётчики в `output` отдельных типов нод («готово 6 из 14» в логах видео-ноды) — это текст лога, а не число. Заводить общее поле имеет смысл вместе с исполнителями, которые будут его писать; пока элемент не нарисован.
- **Потока логов нет.** Строки лежат в `step.logs` и приезжают тем же опросом, что и запуск, поэтому в подвале «показано N из M», а не «поток открыт». SSE или курсорный endpoint — отдельная работа с своим бюджетом на переподключения и обратное давление, и делать её заодно с фильтрами списка значит не сделать ни того, ни другого.
- **Счётчики в заголовке дня считаются по загруженным страницам.** Мета отдаёт разбивку за весь период выборки, а не за каждый день отдельно. Чтобы получить точное «214 за сутки · 4 упало», на общем экране есть фильтр по дню: выбранный день — и счётчики в шапке относятся ровно к нему.

**Этап 6, воронка атрибуции (серверная часть)**

- **Воронка склеена из двух источников, и это видно в контракте.** Тренды, сценарии, ролики и публикации считаются по нашим таблицам, переходы, заявки и продажи — по `AttributionEvent`. У стадии есть `scope`, и от него зависит, какие фильтры к ней применимы. Отбор по площадке и аккаунту стадии производства не сужает: тренд, сценарий и ролик площадке не принадлежат, а один ролик уходит сразу на несколько аккаунтов. Воронка пишет об этом прямо под собой (`productionScopeNote`), а не делает вид, что 34 тренда были «трендами TikTok».
- **Стадии из семи типов событий выбраны три.** `messenger_opened` — переход, `conversion_submitted` — заявка, `sale_attributed` — продажа. Остальные четыре (`automation_comment`, `automation_direct`, `lead_magnet_delivered`, `conversion_opened`) не стали стадиями воронки: первые два — наши собственные действия, а не поведение человека, вторые два видны в разборе публикации, где важна последовательность, а не агрегат.
- **Просмотры — последний замер, а не сумма снимков.** `PostMetrics` хранит накопительные значения, и сумма трёх замеров одной публикации утроила бы просмотры. В воронке `DISTINCT ON (uploadId)` по времени замера, в динамике — прирост между соседними замерами через `LAG`. Тест на это есть: три снимка 200/600/1000 дают 1000, а не 1800.
- **Общей шкалы у столбиков нет, и её не может быть.** Восемьсот тысяч просмотров и сорок роликов на одной оси превращают все стадии, кроме просмотров, в невидимую полоску. Стадия сравнивается с крупнейшей стадией своей величины (`unitGroup`: штуки, просмотры, события), и подпись под воронкой это объясняет. Логарифмическую шкалу не брали: она читается как обычная и врёт молча.
- **Нормы CTR не существует, поэтому провал считается сравнением с собой.** Макет красит стадию переходов «CTR 0,29% при норме 0,8%»; ни одного источника такой нормы у нас нет. Стадия помечается тревожной, если CTR упал больше чем на пятую часть к прошлому окну той же длины, и в тексте стоит прошлое значение, а не выдуманный порог.
- **Стоимость заявки — расход на ролики окна, делённый на заявки окна.** Берётся `Video.totalCostActual` — тот же агрегат, что показывают карточка ролика и список; считать деньги заново по журналу списаний значило бы завести вторую правду. Определение написано прямо под KPI: это не «стоимость лида по всем расходам завода», а отношение двух наблюдаемых величин.
- **Дельта у долей — в процентных пунктах.** «CTR упал на 33 %» и «CTR упал на 0,14 пп» — разные утверждения, и проверяемо второе. Разведено единицей измерения KPI (`unit`), а не догадкой по названию.
- **Первое и последнее касание — разные запросы к одним событиям.** Заслуга за заявку достаётся либо публикации, на которой заявка записана (сходится с CRM), либо первому касанию того же `messengerUserId`. Сшивка — нижняя оценка: события без опознанного человека остаются при своей публикации, потому что связать их не с чем. Тест проверяет ровно расхождение: один человек, две публикации, разные победители у `first` и `last`.
- **Рейтинг хуков берёт вариант сценария, а не гипотезу.** `ScenarioVariant.hook` есть у каждого ролика классического пути, `ContentHypothesis.hook` — только у фабричного. A/B сравнивает варианты внутри одного сценария: тренд, персонаж и аккаунты у них общие, отличается хук — иначе это сравнение двух разных роликов, а не двух версий одного.
- **Источник тренда — площадка и ключевое слово.** Именно так профиль парсинга описывает свою выборку. Сортировка по продажам, а не по числу трендов: пятьсот трендов без продаж стоят ниже двухсот с продажами.
- **Порог графика — три непустых дня, а не семь из макета.** При окне «24 часа» семи дней не существует, и правило из макета выключило бы график навсегда. Меньше трёх точек — вместо графика объяснение, какой отбор его прячет.
- **Ноль и «нет данных» не смешиваются в динамике.** У стоимости заявки в день без заявок столбика нет вовсе (`null`), а не нулевой полосы: делить было не на что, и это другое утверждение, чем «заявка стоила ноль».
- **Разбор публикации не дублирует историю замеров.** Слева — касания по дням из событий атрибуции, справа — переписка автоматизации; графики замеров живут на `/analytics/[uploadId]`, и вторая их копия рядом расходилась бы с первой. Публикация без фабричной записи честно пишет, что tracking token ей не выдавался.
- **Экспорта нет.** Кнопка «Экспорт» из шапки макета не нарисована: endpoint выгрузки не существует, а кнопка, которая ничего не выгружает, хуже её отсутствия.
- **Два сида.** `seed-attribution-demo` не выдумывает переходы: их столько, сколько даёт собственный CTR публикации из `PostMetrics`, а идемпотентный ключ считает та же функция, что и приёмник вебхука. Каждый пятый переход — человек, которого уже видели на другой публикации, иначе переключатель моделей атрибуции показывает одно и то же. `seed-ab-variants-demo` дописывает уже созданным сущностям то, чего им не хватало для рейтингов: гео и ключевое слово тренду, разные хуки вариантам, связь ролика с вариантом и вторую версию ролика у двух сценариев.

## 9. Риски

**Объём.** 341 файл — это не одна сессия. Этапы 0–4 закладывают фундамент и должны делаться внимательно; этап 5 механический и распараллеливается по разделам.

**Скрытая логика в шаблонах.** Часть страниц — до 500 строк, и в разметке может сидеть поведение, которого нет в composables. Перед переписыванием страницы её текущий шаблон читается целиком, а не переносится по памяти.

**Новые сущности.** Сохранённые представления и право `canManageSharedViews` — это миграция БД и серверные endpoints, то есть выход за границы «только UI». Делается в этапе 3 отдельным коммитом.

**E2E ломаются все сразу.** Это ожидаемо и не является регрессией; тесты переписываются в этапе 7, но не позже, иначе ветку нечем проверять.
